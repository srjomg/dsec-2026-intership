# Описание процесса тестирования
## **Общее**
- Проверить все места пользовательского ввода на инъекции (XSS, SQLi, SSTI, и т.д.)
- Проверить все места пользовательского ввода на граничные случаи (0, большое число, пустая строка, и т.д.)
- Проверить возможность неавторизованного использование методов (убрать Cookie)
- Проверить возможность эксплуатации CSRF. 
- Проверить методы на лимиты (особенно `/login` для кейса с брутфорсом)
## **POST `/login`**
- Убрать из запроса пароль, оставив только логин
- Проверить поле `login` на уязвимость к XSS, SSTI, SQLi и т.д. (учитывая то, что, как было видно по запросам, после входа отображается логин)
## **GET `/user-info?id=X`**
- Получить информацию об аккаунте с другим ID (IDOR)
- Попробовать изменить HTTP-метод с `GET` на `POST`, `PUT`, `DELETE` (HTTP Verb Tampering)
- Попробовать найти критичных пользователей (User Enumeration)
## **POST `/update-user-info?id=X`**
- Изменить информацию для аккаунта с другим ID
- Изменить иную информацию: добавить в JSON запроса поля `role`, `status` (Mass Assignment)
## **POST `/buy-item`**
- Указать нулевую цену (бесплатная покупка)
- Указать отрицательную цену (накрутка денег)
- Использовать один промокод два раза
- Попытаться угадать промокод (`50sale`, `sale50` и т.д.)
- Отправить несколько параллельных запросов с покупкой товара, чтобы проверить наличие состояния гонки (например, купить 2 товара заплатив 1 раз).
# Явные уязвимости
## **1. Передача пароля в открытом виде в `/user-info?id=X`**
Получение информации о пользователе раскрывает его текущий пароль.
## **2. Обновление пароля без знания исходного в `/update-user-info?id=X`**
При обновлении пароля не требуется ввода текущего пароля для авторизации действий.
## **3. Обновление информации пользователя без авторизации в `/update-user-info?id=X`**
Обновление информации о пользователе не требует предоставления сессионных Cookie.
## **4. Использование предсказуемых ID пользователей**
Идентификатор пользователя является предсказуемым, что ведет к возможности перечисления учетных записей.
Для эксплуатации достаточно декодировать из Base64 ID: `fromBase64("MjUwMA==") => "2500"`
## **5. Отсутствие флагов безопасности `Secure` и `HttpOnly` у сессионной Cookie**
Отсутствие данных флагов открывает возможности перехвата сессионной Cookie через HTTP или XSS.
# Потенциальные уязвимости
## **1. Использования слабых паролей**
Возможно, приложение позволяет использовать при регистрации слабые пароли, например: "пушистик".
## **2. Манипулирование ценой при покупке товара в `/buy-item`**
***Обоснование**: если цена товара храниться в БД, то зачем её указывать при покупке товара?*

Поэтому, возможно, изменение параметра `price` позволит манипулировать ценой, открывая возможности бесплатной покупки, накрутки денег.
