# Ситуация 1
## Описание
Получен шелл с правами пользователя `user`.
Файл `/etc/shadow` имеет следующие права:
```bash
-rw----rw- root user /etc/shadow
```
где права для
- владельца (`root`): чтение и запись
- группы (`user`): прав нет
- всех остальных: чтение и запись
## Способы повышения привилегий
Пользователь `user`, вероятнее всего, принадлежит группе `user`.

Поэтому, **напрямую прочитать или изменить файл `/etc/shadow` нельзя**.

Однако, если попытаться найти на сервере любой локальный сервис или скрипт, который работает от имени другого непривилегированного пользователя (например `postgres`, `flink` и т.д.), и проэксплуатировать его.

*Например, если на сервере есть веб-приложение с уязвимостью LFI, то веб-шелл запущенный от имени `www-data` не будет состоять в группе `user` и получит доступ чтения и записи к файлу `/etc/shadow`.*
# Ситуация 2
Получен шелл с правами пользователя `user`.
Набор групп пользователя `user`: `user`, `cdrom`, `vboxusers`, `docker`.
Файл `/etc/shadow` имеет следующие права:
```bash
-rw----rw- root adm /etc/shadow
```
где права для
- владельца (`root`): чтение и запись
- группы (`adm`): прав нет
- всех остальных: чтение и запись
## Способы повышения привилегий
1) Пользователь не является `root`, не входит в группу `adm`, поэтому он может прочитать файл `/etc/shadow`.
   Далее, пользователь может:
	- Украсть хеши паролей пользователей и затем подобрать.
	- Перезаписать хеш пароля
		```bash
		openssl passwd -6 <password>
		# затем перезаписать хеш в /etc/shadow
		```
2) Так как пользователь находится в группе `docker`, если у него есть права на запуск контейнеров, он может запустить Docker-демон (который чаще всего работает от имени `root`), а затем примонтировать папку системы для дальнейшей манипуляции с ней (и выполнить те же действий из п. 1).
	```bash
	docker run -v /:/mnt -it alpine chroot /mnt
	# Монтирует корневой каталог системы / в каталог внутри контейнейра /mnt
	# Для контейнера на основе Alpine Linux делает корневым каталогом /mnt 
	```
