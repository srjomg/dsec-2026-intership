# Слабые места приложения
## 1. Некорректно настроенная политика безопасности
Политика безопасности выглядит так:
```json
{
  "email_change_requires_reauth": false,
  "password_reset_invalidate_sessions": false,
  "admin_mfa_required": false,
  "notify_on_sensitive_changes": true
}
```
**Слабые места**:
- Для администраторов не требуется MFA.
- Отсутствие аннулирования всех активных сессий после сброса пароля *(если сессия скомпрометирована, то сброс пароля не поможет)*.
- Не требуется повторная аутентификация для изменения почты.
## 2. Получении избыточной информации о пользователях (IDOR)
API-эндпоинты `/api/v1/users` и `/api/v1/users/{id}` раскрывают избыточную информацию о пользователе (**IDOR**), такую как: номер телефона, почту, логин.
## 3. Получение чужих уведомлений (IDOR)
Приложение не проводит корректную проверку прав при попытке просмотра чужих уведомлений:
```http
GET /api/v1/notifications?user_id=<VICTIM_USER_ID> HTTP/1.1
Host: portal.acme.local
Cookie: SESSIONID=<ANY_SESSIONID>
```
## 4. Избыточное раскрытие информации в уведомлениях
Уведомления через `/api/v1/notification` раскрывают избыточную информацию, такую как **токен сброса пароля**.

В совокупности с возможностью неавторизованного просмотра чужих уведомлений это ведет к возможности захвата аккаунта.
## 5. Изменение информации другого пользователя (Broken Access Control)
Приложение позволяет изменить информацию другого пользователя зная его ID: 
```http
POST /api/v1/profile/update HTTP/1.1
Host: portal.acme.local
Cookie: SESSIONID=<session>
Content-Type: application/json

{
	"user_id": <victim-user-id>,
	"full_name": "<full-name>",
	"email": "hacker@mail.com"
}
```
# Рекомендации по исправлению
- Правильно настроить политику безопасности.
- Убрать избыточную информацию из ответов `/api/v1/users` и `/api/v1/users/{id}`.
- Добавить корректную проверку прав при получении уведомлений в `/api/v1/notifications`.
- В `/api/v1/profile/update` идентифицировать пользователя не по `user_id`, а по `SESSIONID`.
